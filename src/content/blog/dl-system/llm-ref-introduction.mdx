最近在折腾大模型应用时，发现除了模型本身，推理框架也会影响吞吐、延迟和显存利用。这里先记几个基础概念，再看 vLLM 和 SGLang。

## 为什么需要推理框架？

直接调用模型，和同时服务很多请求，是两件事。推理框架还需要处理：

- 请求怎样排队、怎样一起计算
- 不同长度的输入和输出怎样组成batch
- KV Cache怎样分配、复用和回收
- 怎样通过接口持续返回生成结果

## Prefill / Decode / KV Cache

- **Prefill**：处理输入tokens，建立对应的KV Cache。
- **Decode**：逐步生成新token，同时更新缓存。
- **KV Cache**：保存历史token的key和value，避免每步重新计算它们，但当前token仍需与历史上下文做attention。

输入越长、并发请求越多，缓存压力通常越大。所以“模型权重能装进显存”不代表还能支持预期的上下文和并发。

## vLLM

vLLM是推理与服务引擎，先记住两个机制：

- **PagedAttention**：分块管理KV Cache，减少连续预留带来的浪费。
- **Continuous batching**：在生成迭代之间调整活跃请求，让完成的请求退出，新请求加入。

它也提供兼容OpenAI风格的服务接口。这里的“兼容”是接口形式，并不代表不同模型的输出行为完全一致。

## SGLang

SGLang同样有自己的推理服务运行时，也提供表达模型调用的前端接口，不能只把它理解成vLLM外面的一层工作流。

可以关注它的前缀缓存与调度机制。多个请求存在可复用的相同token前缀时，缓存可能减少重复计算；语义相似的文字不一定能命中。

## 怎么比较？

不适合简单分成“vLLM管性能，SGLang管工作流”。两者能力有交集，先确认模型、硬件和所需功能是否支持，再用同一负载比较。

| 指标 | 关注什么 |
| --- | --- |
| TTFT | 提交请求后多久收到首个token |
| TPOT | 首token之后，后续token的平均间隔 |
| 吞吐 | 单位时间完成的请求或输出token数 |
| 显存占用 | 权重、KV Cache和临时缓冲区的开销 |

比较时固定模型、精度、输入输出长度和并发，并说明是否包含排队时间。单请求生成快，不代表高并发下也表现好。

目前先把推理引擎和应用编排分开理解：引擎处理模型执行与请求调度，Agent上层还要处理工具调用、任务状态和失败重试。
